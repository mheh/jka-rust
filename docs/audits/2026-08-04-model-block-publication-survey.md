### A. The current ownership chain

`ModelSlot` (`crates/mp/renderer/src/tr_model/model_pool.rs:62-65`): `generation: u32`, `data: Box<ModelData>`. `ModelData` is a type alias for `model_t` (`model_pool.rs:48`).

`ModelPool` (`model_pool.rs:76-81`): `slots: Vec<ModelSlot>`, `num_models: i32`. The type doc states the pool is deliberately not `Clone` and never enters an `Arc`-published registry (`model_pool.rs:12-15`), and names the reason `Box` is load-bearing: `model_pool.rs:58-61` reads "`Box` is load-bearing — `G2_API.cpp:2716` caches the registered `model_t *`, and the DEC-35 mdx views read the `mdxm`/`mdxa` blocks out of this entry, so the entry's address must not move when the pool grows." The cited oracle line, `oracle/codemp/ghoul2/G2_API.cpp:2716`, is `ghlInfo->currentModel = R_GetModelByHandle(ghlInfo->mModel);` inside `G2_SetupModelPointers` — Raven's `CGhoul2Info` caches the `model_t*` result of that call.

`RenderModels` (`crates/mp/renderer/src/tr_model/render_models.rs:46-123`), every field: `models: ModelPool` (:58), `hash: HashMap<String, qhandle_t>` (:66), `cached: BTreeMap<String, CachedEndianedModelBinary>` (:73), `current_level: i32` (:78), `prev_map_name: String` (:84), `inside_register_model: bool` (:90), `num_bsp_models: i32` (:96), `skins: Vec<ServerSkin>` (:104), `server_shaders: Vec<String>` (:113), `bmodel_indices: HashMap<qhandle_t, usize>` (:122).

`model_t` (`crates/mp/renderer/src/tr_local/model_s.rs:28-44`): `name: [c_char; MAX_QPATH]`, `r#type: modtype_t`, `index: c_int`, `dataSize: c_int`, `md3: [*mut md3Header_t; 3]`, `mdxm: *mut mdxmHeader_t`, `mdxa: *mut mdxaHeader_t`, `numLods: c_int`, `bspInstance: qboolean`. Raven's `bmodel` link is dropped; a brush model resolves through `RenderModels::bmodel_index` instead (`model_s.rs:22-24`).

The md3/mdxm/mdxa byte blocks are physically owned by `CachedEndianedModelBinary.disk_image: Option<AlignedBytes>` inside `RenderModels.cached` (`crates/mp/renderer/src/tr_model/cached_model_binary.rs:104-159`). `RenderModels::re_register_server_models_malloc` (`cached_model_binary.rs:248-296`) ingests the buffer into that `AlignedBytes` and returns its base pointer. The loaders then cast that pointer straight into `model_t`'s pointer fields: `server_load.rs::server_load_mdxa` writes `model.mdxa` (`crates/mp/renderer/src/tr_model/server_load.rs:321-322`), `server_load_mdxm` writes `model.mdxm` (`server_load.rs:429-430`), and `frontend.rs::r_load_md3` writes `model.md3[lod]` (`crates/mp/renderer/src/tr_model/frontend.rs:554-555`).

No Rust code holds a raw `model_t*` today. `render/bone_cache.rs:14-20` states plainly that the ghoul2 crate "never names `model_t`/`mdxaHeader_t`" — its `CBoneCache::model` field is a `qhandle_t`, not a pointer (`crates/mp/engine/ghoul2/src/render/bone_cache.rs:130-134`). `RenderModels::get_model` hands back a `&ModelData` by reference on each call (`render_models.rs:220-222`); nothing stores that reference past the call. The only place a `model_t*`-equivalent lives long-term is the pool's own `Box<ModelData>` entries — self-owned, never handed out as a pointer.

### B. The consumers

DEC-35 mdx views: `EngineHost::model_mdxm`/`model_mdxa` (`crates/mp/host-interface/src/engine_host.rs:161,176`; impl at `crates/mp/engine/qcommon/src/common/engine_host_view.rs:268,297`) return `Option<MdxmRef<'static>>`/`Option<MdxaRef<'static>>`, resolved through `RenderModels::model_mdxm_ptrs`/`model_mdxa_ptrs` (`cached_model_binary.rs:328-376`), which read `model.mdxm`/`model.mdxa` plus the DEC-35 parse-once sidecar stored beside the block. `MdxmRef`/`MdxaRef` (`crates/mp/host-interface/src/mdx/mdxm.rs:511-514`, `crates/mp/host-interface/src/mdx/mdxa.rs:269-272`) expose read-only accessors only. No mutation path exists on either type.

The ghoul2 crate's readers (`crates/mp/engine/ghoul2/src`) call `host.model_mdxm`/`host.model_mdxa` at dozens of sites: `bones.rs:825,827`, `api_collision.rs:274`, `api_models.rs:206,219,772`, `misc.rs:228,291,325,329,367,406,419,492,626,1332,1420`, `surfaces.rs:164,192,204,234,296,327,338,368,466,485,492,624,682,726,746`, `render/bone_cache.rs:191`, `render/skeleton.rs:406,450`, `api_saveload.rs:204,255`, `api_surfaces.rs:225`. Every one is a read; the crate needs `MdxmRef`/`MdxaRef` types and no mutation of the underlying block.

Renderer's own MD3 draw path: `tr_mesh.rs::r_add_md3_surfaces` (`crates/mp/renderer/src/tr_mesh.rs:352-537`) dereferences `model.md3[lod]` raw pointer directly (`unsafe`) to read `numFrames` (:372-377), the LOD-resolved header (:404-406), the cull bbox (:410), the fog volume (:427), and the per-surface walk over `ofsSurfaces` stepping by each surface's own `ofsEnd` (:432-536) — surface name, shader count, `md3Shader_t` array. It needs read-only `*const md3Header_t`. The actual frame-interpolated vertex geometry is not read here: `R_AddDrawSurf` stores only `SurfaceGeometry::Md3(Md3SurfaceRef { h_model, lod, surface_index, frame, old_frame, backlerp })` (`crates/mp/renderer/src/tr_main.rs:262-277`, pushed at `tr_mesh.rs:516-531`) — a `Copy` handle-plus-scalars, no pointer — because "the backend decodes per frame" (`tr_main.rs:211-212`). That backend decode does not exist yet in this repo.

Sim-side golden harness path: `tr_main.rs:2017-2088` gates the whole MD3/Ghoul2 arm on an optional `entity_host: Option<&mut EngineHostView>` — when `None`, it prints a one-time warning and draws nothing (`tr_main.rs:2024-2032`); when `Some`, `MOD_MESH` calls `r_add_md3_surfaces` with `models: &RenderModels` (`tr_main.rs:2033-2053`), and `MOD_MDXM`/`MOD_BAD`-with-ghoul2 call `r_add_ghoul_surfaces` (`tr_main.rs:2060-2088,2104-2119`) through `engine_view`. This is the only place `RenderModels` and the ghoul2 draw path meet the frontend walk today, and it needs both read-only block access and the `EngineHost` seam.

### C. The publication precedent

`RenderAssets` (`crates/mp/renderer/src/render_state/render_assets.rs:1-211`) derives `Clone`, required by `Arc::make_mut` (:19-23). It holds `Arena<K>` registries keyed by `Handle<K>` — `images: Arena<ImageAsset>` (:27), `shaders: Arena<ShaderAsset>` (:78), `skins: Arena<SkinAsset>` (:112) — plus `world: Option<Arc<WorldAsset>>` (:147), a nested `Arc` for the single largest asset. The struct's own comment retires the model registry from this struct outright: "`tr.models[]`/`tr.numModels`/`mhHashTable` keep their arena mechanics in place on `RenderModels` ... Unifying the server and client model registries is deferred to the client-engine island" (`render_assets.rs:133-139`).

`RenderAssetsSim` (`crates/mp/renderer/src/render_state/render_assets_sim.rs:13-28`) owns `published: Arc<RenderAssets>`. Its doc states the publish mechanics exactly: registration calls `Arc::make_mut(&mut self.published)`, "which mutates the existing allocation in place when the render thread holds no other reference and clones once when it does. That is ordinary copy-on-write with no locks. The result becomes visible to the render thread at the next frame boundary" (`render_assets_sim.rs:13-21`). `FramePackage.assets: Arc<RenderAssets>` (`crates/mp/renderer/src/render_state/frame_package.rs:42`) is the per-frame `Arc` clone the render thread actually reads: "Cloning the `Arc` is what keeps the render thread off the sim's registry" (`frame_package.rs:40-42`).

`Handle<K>` (`crates/mp/renderer/src/render_state/handle.rs:19-23`): `index: u32`, `generation: u32`, `PhantomData<fn() -> K>`. `Copy`/`Clone`/`PartialEq`/`Hash` are hand-written, not derived, because `K` is a marker type only (:50-75). `Handle::slot_zero()` (:37-39) is the pre-populated default entry.

`WorldGeneration` (`crates/mp/renderer/src/render_state/world_generation.rs:23-29`) is the one-shot contrast: `world: Option<Arc<WorldAsset>>` is `Some` only on the frame the world changed, "nothing there on every other frame" (:9-14), and it is "the same `Arc` the published registry holds, so this costs a refcount, not a copy" (:24-25). `FramePackage.world: Option<WorldGeneration>` (`frame_package.rs:39`) carries it across the channel exactly once. Nothing in this scheme currently touches the model registry — that gap is exactly what DEC-65 ruling 1 closes.

### D. What MD3/Ghoul2 drawing render-side actually needs

MD3: `r_add_md3_surfaces` (`tr_mesh.rs:352-537`) reads, per frame: `md3[0].numFrames` (:372-377), the LOD-selected header `md3[lod]` (:404-406), that header's `ofsSurfaces`-based surface walk with per-surface `numShaders`/`name`/`md3Shader_t[]` for skin and shader resolution (:432-536). `RefEntity` supplies `frame`/`old_frame`/`backlerp` (`crates/mp/renderer/src/render_state/placeholders.rs:135,139,143`) plus `origin`, `customShader`, `customSkin`, `skinNum` (consumed at :410,427,440-500). Tags are not read on this path (no `md3Tag_t` walk inside `r_add_md3_surfaces`; the tag reader `r_get_tag`/`lerp_tag` lives separately in `frontend.rs:202-266,298-325` for `RE_LerpTag`, a distinct entry point). Frame-interpolated vertex/triangle data is deferred entirely: the stored `Md3SurfaceRef` (`tr_main.rs:262-277`) carries `h_model`, `lod`, `surface_index`, `frame`, `old_frame`, `backlerp` and nothing else, so step-003's backend draw is what will need to walk `md3[lod]` down to the named surface and read both frames' vertex arrays, blended by `backlerp` — that decode function does not exist in this repo yet.

Ghoul2: the mdxm surface reads (`crates/mp/host-interface/src/mdx/mdxm.rs`) are `find_surface`/`surf_hierarchy` (:152-162,541-560) yielding per-surface `triangle`/`vert`/`texcoord`/`bone_ref` (:261-293). The mdxa bone reads (`crates/mp/host-interface/src/mdx/mdxa.rs`) are `skel`/`frame_bone_pool_index`/`comp_bone` (:274-315), consumed by `CBoneCache`'s transform chain (`crates/mp/engine/ghoul2/src/render/bone_cache.rs`, `render/bone_transform.rs`) to produce per-bone matrices sim-side. Per DEC-65 ruling 2 (`docs/decisions.md:1532`), that transform now runs sim-side at scene-add time and crosses to the render thread as plain per-entity bone matrices — so step-003's render-side ghoul2 draw needs the mdxm surface geometry (vertices/triangles per surface/LOD) plus the already-computed bone matrices from the frame package, not a live `mdxa` block at draw time.

### E. Send/immutability facts

Post-load writes into a loaded block, all instances found:

- `server_load.rs::register_server_model`'s own LOD-duplicate loop writes `m.md3[l] = m.md3[l+1]` (`server_load.rs:235-241`) — inside the same registration call, before the handle is returned to any consumer. Not a post-completion write.
- `cached_model_binary.rs::poke_shader_index` (`cached_model_binary.rs:456-478`) writes an `i32` into a live `disk_image` at a previously recorded byte offset. This is a real post-load in-place byte mutation, but it is reachable only from the client-only shader-poke replay in `frontend.rs:423` (`re_register_models_malloc`); the doc on `CachedEndianedModelBinary::shader_register_data` states the dedicated server "never replays it" (`cached_model_binary.rs:123-127,282-284`). The dedicated-server load path this ruling targets never exercises this write.
- Eviction removes whole cache entries — `re_register_models_delete_all` (`cached_model_binary.rs:632-636`), `models_level_load_end` (:493-556), `re_register_models_dump_non_pure` (:567-592) — via `BTreeMap::remove`, dropping `AlignedBytes`. None of these rewrite bytes in place; they delete the entry.
- `ModelPool::reset` (`model_pool.rs:168-174`) bumps every live slot's generation and drops `num_models` to 0; it does not touch the `md3`/`mdxm`/`mdxa` bytes themselves. The next `alloc()` overwrites that slot's `Box<ModelData>` with a fresh zeroed entry (`model_pool.rs:140-150`), dropping the old `model_t`, but the corresponding `CachedEndianedModelBinary` entry's bytes are freed later and separately, by a level-load-end/delete-all pass, not synchronously with `reset`.

Reset/eviction triggers found: `RenderModels::model_init` runs at renderer init in `crates/mp/renderer/src/tr_init.rs:1755` (vid_restart/`R_Init`) and at dedicated-server startup in `crates/mp/engine/server/src/sv_renderer.rs:36` (`R_SVModelInit`). `RenderModels::hunk_clear` runs from the `R_HunkClearCrap` hook (`crates/mp/renderer/src/hook_install.rs:124-127`). `RenderModels::media_level_load_begin` runs from `sv_renderer.rs:56` on map load, deleting all cached models on `eForceReload_MODELS`/`ALL` or dumping non-pure entries under `sv_pure`. `RenderModels::models_level_load_end` runs from `crates/mp/engine/client/src/cl_cgame.rs:1222` (client level-load-end) and from a z_malloc-fail-recovery hook (`hook_install.rs:119`), evicting stale-level entries against the `r_modelpoolmegs` budget (`cached_model_binary.rs:510-513`).

Conclusion: with the one narrow exception above (a client-only path the dedicated-server track never runs), the loaded blocks are write-once-then-read between registration and eviction, and eviction is always whole-entry removal, never an in-place edit. DEC-65's claim that "the blocks are immutable after load" (`docs/decisions.md:1530`) holds under this survey, modulo that documented exception.

### F. Size and layout

No existing per-model byte accounting beyond `RenderModels::modellist_f` (`render_models.rs:232-256`, prints `dataSize` and LOD count per model) and `RenderModels::get_model_data_alloc_size` (`cached_model_binary.rs:638-649`), which sums `CachedEndianedModelBinary::alloc_size` (== `AlignedBytes::len`, doc at `cached_model_binary.rs:114-119`) across the cache. No fixture or oracle-cited absolute byte sizes for a typical `.md3`/`.glm`/`.gla` file are recorded in-repo; the only size-budget knob is the `r_modelpoolmegs` cvar gate (`cached_model_binary.rs:510-513`), and `MAX_MOD_KNOWN = 1024` (`model_pool.rs:41`) caps entry count, not total bytes.

Address-stability requirements beyond the `ModelPool` Box-pin contract (A):

- `AlignedBytes` itself carries an independent pinning requirement: "heap-pinned/address-stable" because "the frozen ghoul2 seam derefs raw pointers into it across frames — `CBoneCache` parent-seeding, skeleton build, per-call ragdoll basepose" (`crates/mp/renderer/src/tr_model/aligned_bytes.rs:13-15`, citing `tr_ghoul2.cpp:416-421,614-615`). This block must not move even independently of the enclosing `CachedEndianedModelBinary`/`BTreeMap`.
- `CBoneCache.mdxa: Option<MdxaRef<'static>>` (`render/bone_cache.rs:129`) is exactly the cached-pointer case F asks about — a `'static` reference into a loader block, stored inside `Ghoul2System.bone_caches` (`crates/mp/engine/ghoul2/src/ghoul2_system.rs:152`) across calls. It is not held indefinitely: `render/skeleton.rs:450,486-487` re-fetches `host.model_mdxa(ghoul2.model)` and re-stores it into `cache.mdxa` at the top of every `g2_transform_ghoul_bones_inner` call, with an early return on eviction (`skeleton.rs:450-456`) — so its live window is one transform pass, not the cache's whole lifetime.
- No self-referential absolute offsets were found. Every mdx accessor (`mdxm.rs`, `mdxa.rs`) recomputes its byte offset fresh from the block's own header fields on each call (for example `find_surface` at `mdxm.rs:152-162`, `skel` at `mdxa.rs:85-90`) rather than caching an absolute address. The one exception, `MdxaSkelView::base_pose_mat_ptr`/`base_pose_mat_inv_ptr` (`mdxa.rs:163-170`), hands back a raw `*const mdxaBone_t` into the block — but a repo-wide search finds zero call sites for either beyond their own definitions, so this is unused, not a live pinning hazard.

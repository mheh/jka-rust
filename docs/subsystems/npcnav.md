## Raven ground truth

### Frame role and lifecycle

`CNavigator navigator` is a single file-scope global
(`oracle/codemp/server/NPCNav/navigator.cpp:32`) living in the **engine**, not
the game module: the comment at :33-34 states the nav code moved into the engine
and the game reaches it only through `trap_*` syscalls. Its ctor
(:478-484) lazily runs `NAV_CvarInit` (:39-43) to register `d_altRoutes` and
`d_patched` (both `CVAR_CHEAT`). `Init()` (:572-575) just calls `Free()`
(:583-594), which `delete`s every `CNode*` and clears `m_nodes` +
`m_edgeLookupMap`.

The graph is populated one of two ways:
1. **Load** from `maps/<name>.nav` (:602-657): validates `NAV_HEADER_ID`
   (`'JNV5'`, navigator.h:21) and a checksum, then reads `numNodes` `CNode`s
   (each via `CNode::Load`, :426-470, which reads position/flags/id/radius, its
   edge vector, and its per-node rank array), then reads the `failedEdges[]`
   array and rebuilds `m_edgeLookupMap`.
2. **Built live**: `AddRawPoint` (:710-726) appends a node; `HardConnect`
   (:1113-1140) or `CalculatePaths` (:884-908) wires edges; `Save` (:665-702)
   writes it back out. (This is exactly the build path `tools/npcnav-oracle`
   drives to emit the golden `.nav` fixtures — NAV-D3.)

`CalculatePaths` (:884-908) allocates each node's rank table
(`CNode::InitRanks`, :351-363) then runs `CalculatePath` (:814-877) — a
priority-queue flood fill from each node that fills `m_ranks[targetID] = rank`
for every reachable node. It is pure graph work (no traces). It then calls
`GNavCallback_CP_FindCombatPointWaypoints` (unless `recalc`) and sets
`pathsCalculated = qtrue`.

### Data flow — the graph

- `CNode` (navigator.h:70-126): `m_position` (vec3), `m_flags`, `m_radius`,
  `m_ID`, a `vector<edge_t>` (`edge_t = {int ID; int cost; BYTE flags}`,
  navigator.h:72-77), and a heap `int *m_ranks` (one rank per node,
  `-1`-initialised, navigator.cpp:351-363). `m_numEdges` caps at 8
  (`assert(m_numEdges < 9)`, :182). Edges are stored bidirectionally
  (`SetEdgeCost`/`HardConnect` add to both endpoints, :778-779, :1138-1139).
- `CEdge` (navigator.h:50-62): `{m_first, m_second, m_cost}` — reused by the
  priority queue as a generic `(node, root, cost)` triple, **not** a stored
  graph edge.
- `m_edgeLookupMap` (`multimap<int,int>`, navigator.h:40,248): maps a failed
  edge's `startID` → its index in `failedEdges[]`, so `EdgeFailed`
  (:1876-1923) does `equal_range` lookups instead of a linear scan.
- `failedEdges[MAX_FAILED_EDGES]` (`MAX_FAILED_EDGES = 32`, navigator.h:133,245):
  fixed array of `failedEdge_t {int startID, endID, checkTime, entID}`
  (`oracle/codemp/game/g_public.h:52-58` — the struct is **shared** with the
  game module and crosses the seam by pointer via `G_NAV_CLEARFAILEDEDGE` /
  `G_NAV_CHECKFAILEDEDGE`).

### The priority queue

`CPriorityQueue` (navigator.h:254-276) wraps a `vector<CEdge*> mHeap` driven by
`std::push_heap`/`std::pop_heap` with comparator `NodeTotalGreater`
(:2693-2699, `first->m_cost > second->m_cost` — a **min-heap on cost**). It
owns raw `CEdge*` allocated by `new` in `CalculatePath`; `Pop` returns the
pointer and the caller `delete`s it (:869), the dtor drains and deletes the
rest (:2705-2711). `Push` = `push_back` + `std::push_heap`; `Pop` = read
`front()`, `std::pop_heap`, `pop_back` (:2731-2758). `Find`/`Update`
(:2716-2774) linear-scan `mHeap` by `m_first`.

`CalculatePath` (:814-877) drives it: seed the frontier with each direct edge,
then repeatedly `Pop` the min-cost `CEdge`, assign the popped node
`node->AddRank(testNode->GetID(), curRank++)` (:853), and `Push` each unchecked
neighbour at cumulative cost. **The `curRank++` is assigned in pop order**, so
the order in which equal-cost frontier entries pop is baked into every node's
rank table — the tie-break is parity-visible (NAV-D3, RULING 26).

### The failed-edge / checked-node bookkeeping

- Per-entity failed **nodes** live on `sharedEntity_t`
  (`oracle/codemp/game/g_public.h:706-712`: `waypoint`, `failedWaypoints[8]`
  (`MAX_FAILED_NODES = 8`, g_public.h:673), `failedWaypointCheckTime`), written
  by `AddFailedNode` (:1768-1799) / re-tested by `CheckFailedNodes`
  (:1724-1766) / read by `NodeFailed` (:1801-1811). The `CNavigator` methods
  reach these fields by **dereferencing the `sharedEntity_t *ent` the trap
  hands them** (`(sharedEntity_t *)VMA(1)`, sv_game.cpp:885/888/891), exactly as
  Raven does — see NAV-D3. `CheckFailedNodes`'s recheck stamp is
  `svs.time + CHECK_FAILED_EDGE_INTERVAL + Q_irand(0,1000)` (:1763) — `svs.time`
  via `sv_time` (NAV-D3), the jitter via `host.irand` (NAV-D3 / RULING 39c).
  `AddFailedNode` stamps `failedWaypointCheckTime = svs.time +
  CHECK_FAILED_EDGE_INTITIAL` (:1778,:1797 — a **different** constant, **no**
  `Q_irand` jitter; `svs.time` via `sv_time`).
- Failed **edges** live in the engine's `failedEdges[]` + `m_edgeLookupMap`;
  `AddFailedEdge` (:1925-2055), `ClearFailedEdge` (:1835-1865),
  `ClearAllFailedEdges` (:1867-1874), `CheckFailedEdge` (:2057-2142),
  `CheckAllFailedEdges` (:2144-2168). The `checkTime` stamps at :1987 and :2137
  are the same `svs.time + CHECK_FAILED_EDGE_INTERVAL + Q_irand(0,1000)` shape
  (NAV-D3 `sv_time` + `host.irand`).
- `CheckedNode`/`SetCheckedNode`/`ClearCheckedNodes` (:1688-1719) memoise
  per-(waypoint,ent) trace results in a file-scope `static map<int,byte>
  CheckedNodes` (:1687) keyed `wayPoint*MAX_GENTITIES+ent`, values
  `CHECKED_NO/FAILED/PASSED` (:54-56). This is genuine cross-call state (fork-3
  kind-3), reset by `ClearCheckedNodes`.

## Decisions

**NAV-D1** — Every Win32 `long`/`unsigned long` field inside the `.nav`
**binary format** is pinned to **exactly 4 bytes** — `i32` for the signed
`GetLong` value, `u32` for the `unsigned long` header ids — and **never**
`core::ffi::c_long`/`c_ulong`. Per **RULING 44** (2026-07-09, closing NAV-Q16) the
only `.nav` fields typed `long`/`unsigned long` are the NAV header id
(`long navID = GetLong( file )` navigator.cpp:614; `unsigned long id =
NAV_HEADER_ID` :676) and the NODE header id (`unsigned long header` — write :388,
read :428), the signed one read incrementally by `GetLong` (:557-564); every
other `.nav` field (position/flags/id/radius/numEdges/checksum/numNodes/ranks) is
`int`/`float`, already unambiguously 4 bytes. `tools/npcnav-oracle` (NAV-D3)
builds the **unmodified** `navigator.cpp` TU with a **4-byte-`long` shim** —
applied through compile flags / a stub-header typedef, **not** a source edit (the
pinned-parse-config `LittleShort=` precedent) — so the fixtures it emits are
retail-shaped (Win32 ILP32, 4-byte `long`); the goldens, retail pk3 `.nav` files,
and the OpenJK referee therefore all agree on the 4-byte header-id width. The
width is stated at every affected row of the State-ownership and
Method-transcription tables. This **overturns** the earlier pass's LP64-`c_long`
reading of these fields. **GENERAL RULE (recorded in Divergences):** a Win32
`long` in any binary FILE format is 4 bytes (`i32`/`u32`); a `c_long` in a
compiled-ABI struct is the **separate, correct** case (that is where
`core::ffi::c_long` belongs — e.g. `crates/mp/engine/icarus/src/blockstream/
cblock_stream.rs`, `crates/mp/qshared/src/common/mp/botlib/botlib_import_s.rs`).
Rejected `c_long`/`c_ulong` at the `.nav` sites (8 bytes on LP64 hosts — desyncs
the golden byte layout from retail `.nav` files and the referee). Closes NAV-Q16.
(RULING 44, 2026-07-09.)

**NAV-D2** — This doc **states the libstdc++ `push_heap`/`pop_heap` sift
algorithm behaviorally** (Verification strategy → "The libstdc++ heap sift"),
precisely enough that a porter implements the faithful `PriorityQueue` (NAV-D3,
D-7) **from the doc alone**, with only a reference-only cite to the header path —
**no GPL source text copied into the repo**. Per **RULING 45** (2026-07-09,
completing rulings 18/26, closing NAV-Q17) the behavioral spec is the two-phase
Floyd shape: `pop_heap` moves the root (the least-cost element under
`NodeTotalGreater`) out as the result, `__adjust_heap` percolates the resulting
hole **down** to a leaf using libstdc++'s child-comparison order, then
`__push_heap` sifts the saved value **up** from that leaf; `push_heap` is the same
sift-up from the just-appended leaf. The reference-only cite (allowed porter
reading, GPL text stays out) is the Homebrew g++-16 `bits/stl_heap.h` that
`tools/npcnav-oracle` already links (NAV-D3). The **enforcing gate** is the
committed rank-order goldens: `CalculatePath` bakes pop order into every node's
rank table via `curRank++` (navigator.cpp:853), so any sift-order mistake fails
byte-comparison. Rejected `std::BinaryHeap` (different sift/tie order) and
asserting the sift blind (the goldens must bind it). Closes NAV-Q17. (RULING 45,
2026-07-09.)

non-width, non-heap portions). The prior-round rulings and the load-bearing

**The libstdc++ heap sift (NAV-D2 / RULING 45 — behavioral spec a porter
implements from).** The faithful `PriorityQueue` (NAV-D3, D-7) hand-transcribes
the libstdc++ `push_heap`/`pop_heap` sift onto an owned `Vec<Edge>` under the
comparator `NodeTotalGreater` — `comp(a, b) = a.cost > b.cost`. Under that
comparator the structure is a **min-heap on `cost`**: the "greatest under `comp`"
element (least cost) sits at the root (`Vec` index 0), each node's children are at
`2*i+1` and `2*i+2`, and the invariant is `!comp(child, parent)` everywhere.
Implement the two operations exactly as follows (this is the enforced order; the
rank goldens below bind it byte-for-byte, so no step is optional):

- **`Push(value)` — `push_back` then sift UP (`__push_heap`).** Append `value` at
  the tail; set the *hole* to that leaf index (`len-1`). While the hole is above
  the root, compute its parent `(hole-1)/2`; if `comp(parent, value)` — the parent
  is *less* than `value` under `comp`, i.e. the parent's cost is greater — move the
  parent's value **down** into the hole and raise the hole to the parent index;
  otherwise stop. Write `value` into the final hole.
- **`Pop()` — `__pop_heap` = move root out, then `__adjust_heap` (two-phase
  Floyd).** Read the result from the root (`front()`, the least-cost element).
  Take the *last* element's value out as the `saved` value and shrink the logical
  length by one. Now re-seat `saved` starting from a hole at the root:
  - **Phase 1 — sift the HOLE down to a leaf.** Repeatedly, while the hole has two
    children: look at the **second (right) child** `2*hole+2`; if
    `comp(right_child, left_child)` (the right child is *less* under `comp`, i.e.
    its cost is greater), step the chosen child back to the **left** child
    `2*hole+1`; otherwise keep the right. Move the chosen child's value **up** into
    the hole and descend the hole to that child's index. A final single-child
    fix-up handles the even-length last-parent case (a hole whose only child is the
    left one): move that lone left child up into the hole and descend. This walks
    the hole all the way to a leaf **without comparing against `saved`** — the
    defining property of the Floyd variant.
  - **Phase 2 — sift `saved` UP from the leaf (`__push_heap`).** From the leaf hole
    Phase 1 produced, run the same sift-up as `Push`: while `comp(parent, saved)`,
    move the parent down and raise the hole; write `saved` into the final hole.

  The child-comparison order (visit the right child, step to the left only when
  `comp(right, left)`) and the two-phase shape are precisely what fix the
  equal-cost tie order. Reference-only cite (allowed porter reading; **no source
  text is copied into the repo — GPL text stays out**): the Homebrew g++-16
  `bits/stl_heap.h` `tools/npcnav-oracle` links — `std::__push_heap` (sift-up),
  `std::__adjust_heap` (the two-phase down-then-up), `std::__pop_heap` (root-move
  then `__adjust_heap`); on the current host the version-pinned path is
  `/opt/homebrew/Cellar/gcc/16.1.0/include/c++/16/bits/stl_heap.h`. **Enforcing
  gate:** `CalculatePath` assigns `node->AddRank(testNode->GetID(), curRank++)` in
  **pop order** (navigator.cpp:853), so the pop sequence — including every
  equal-cost tie — is baked into every node's rank table; the committed rank
  goldens `tools/npcnav-oracle` dumps from that same libstdc++ fail byte-comparison
  on any sift-order mistake. So the transcription is verified against the exact
  implementation it must match, never asserted blind.

## Divergences

Per porting-rules §19 (diverge only where Raven is UB; note ≤2 lines at the
site; keep out of shared fixtures) and §20 (preserve emergent quirks; drop dead
surface). `port-cpp-subsystem` consumes this list.

- **D-1 (UB):** `CEdge::CEdge(void)` (:82-85) calls `CEdge(-1,-1,-1)` which
  constructs a *discarded temporary* — the real object's `m_first/second/cost`
  are left **uninitialised**. The 0-arg ctor has no live caller (queue nodes use
  `new CEdge(a,b,c)`; graph edges use the inner `edge_t`). Port `Edge` without a
  meaning-bearing `Default`; if one is required, use `Edge{-1,-1,-1}` (the
  author's evident intent). Keep out of fixtures.
- **D-2 (preserved quirk):** `CNode::GetEdge*`/`SetEdgeFlags` bound-check with
  `edgeNum > m_numEdges` not `>=` (:246,273,300,327). Faithful `>` kept; the
  off-by-one is harmless (the `count` scan never matches `edgeNum ==
  m_numEdges`, returns the fallback).
- **D-3 (dead path):** `AddRawPoint` (:714-718) tests `node == NULL` after
  `CNode::Create` (C++ `new` throws, never returns NULL) → the `Com_Error`
  branch is unreachable. Rust `Node::create` is infallible; port the error
  branch as unreachable/omitted with a §20 note.
- **D-4 (dead branch):** `CheckFailedEdge` (:2100-2118) `#if 0` selects the
  `SV_Trace` `#else` arm; the `NAVNEW_ClearPathBetweenPoints` arm does not
  compile. Port only the live `#else`.
- **D-5 (preserved bug):** `GetNearestNode` (:1572-1579) has `if (...==
  CHECKED_FAILED) ... else if (... == CHECKED_FAILED)` — the second branch is a
  duplicate of the first (dead; likely meant `CHECKED_PASSED`). Preserve
  bug-for-bug (§20).
- **D-6 (release-elided assert):** `AddEdge`'s `assert(m_numEdges < 9)` (:182)
  and the `assert(m_ranks)`/`assert(ent...)` sites compile out under `NDEBUG`.
  Port as `debug_assert!` (no release-path behavior change).
- **D-7 (idiomatic ownership, faithful order):** `CPriorityQueue`'s raw `CEdge*`
  `new`/`delete` lifecycle (:818,838,865,869,2705-2758) becomes an owning
  `Vec<Edge>` of values with the libstdc++ `push_heap`/`pop_heap` sift algorithm
  hand-transcribed. **The sift is spelled out behaviorally in NAV-D2 (RULING 45),
  Verification strategy → "The libstdc++ heap sift"** — the two-phase Floyd shape
  (`pop_heap` moves the root out, `__adjust_heap` percolates the hole down to a
  leaf under libstdc++'s child-comparison order, `__push_heap` sifts the saved
  value up from the leaf), precise enough to implement from the doc alone. The
  **reference-only** cite (allowed porter reading; **no source text copied into the
  repo — GPL text stays out**) is the Homebrew g++-16 `<bits/stl_heap.h>` the
  `tools/npcnav-oracle` harness links (RULING 26 / NAV-D3 — the same libstdc++
  whose ties the goldens are pinned to): `std::__push_heap`, `std::__adjust_heap`,
  `std::__pop_heap`, reached from the public `push_heap`/`pop_heap`; a §F porter
  already has this toolchain in-environment (compiles the oracle TU for goldens,
  porting-rules §18), and the version-pinned path on the current host is
  `/opt/homebrew/Cellar/gcc/16.1.0/include/c++/16/bits/stl_heap.h`. The exact sift
  order is **not asserted blind**: the committed rank goldens `tools/npcnav-oracle`
  dumps from that same libstdc++ (`CalculatePath`'s `curRank++` bakes pop order
  into every rank table, navigator.cpp:853) are the **binding differential check**,
  so the transcription is verified byte-for-byte against the implementation it must
  match. Ownership/layout is free (§F); pop order under `NodeTotalGreater` —
  including equal-cost ties — is preserved to match libstdc++. **Not**
  `std::BinaryHeap` (would diverge tie order). `Find`/`Update` (:2716-2774) have no
  live caller — drop with §20 zero-caller notes.
- **D-8 (UB):** `CNavigator::GetNodeRadius` (:1029-1034) guards only
  `m_nodes.size()==0`, never the `nodeID` range — an out-of-range `nodeID` on a
  **non-empty** graph is unchecked `m_nodes[nodeID]` Vec-index UB (every sibling
  accessor guards `nodeID < 0 || nodeID >= m_nodes.size()`: `GetNodePosition`
  :2447, `GetNodeNumEdges` :2465, `GetNodeEdge` :2483). Per §19 and the engine §F
  unchecked-index policy (engine-fork-discovery RULING 15 — guard-and-return),
  add the sibling range guard and return the function's **own** existing
  empty-graph sentinel `0` (:1032). ≤2-line note at the site; keep the UB path
  out of fixtures.
- **D-9 (Win32 `long` width in the `.nav` binary format — GENERAL RULE, NAV-D1 /
  RULING 44):** the `.nav` blob's `long`/`unsigned long` header-id fields (`long
  navID`/`unsigned long id` navigator.cpp:614/676; `unsigned long header`
  :388/:428) are **exactly 4 bytes** — `i32`/`u32`, **never** `core::ffi::c_long`/
  `c_ulong`. **General rule this record establishes for the whole port:** a Win32
  `long` inside any binary **FILE format** is 4 bytes (Win32 is ILP32; the retail
  `.nav` blobs were written that way); a `c_long` in a **compiled-ABI struct** or
  extern-fn signature is the *separate, correct* `core::ffi::c_long` case (e.g.
  `CBlockStream.m_fileSize`/`m_streamPos` in
  `crates/mp/engine/icarus/src/blockstream/cblock_stream.rs`, `FS_Seek`'s offset in
  `crates/mp/qshared/src/common/mp/botlib/botlib_import_s.rs`) — those are runtime
  layout, not on-disk bytes, so their width follows the host ABI. The two cases are
  distinct; do not cross-apply. `tools/npcnav-oracle` builds the unmodified TU with
  a 4-byte-`long` shim (NAV-D1) so its emitted fixtures are retail-shaped, keeping
  this out of the shared-fixture ambiguity. This **corrects** the earlier pass,
  which read these `.nav` fields as LP64 `c_long` (8 bytes) and argued host
  self-consistency instead of retail parity.

- **NAV-Q16** — *(Resolved: NAV-D1 / RULING 44, 2026-07-09.)* **What byte width do
  the `.nav` binary format's `long`/`unsigned long` fields (the `GetLong` value and
  the NAV/NODE header ids, navigator.cpp:388,428,557-564,614,676) take in Rust —
  `c_long` (8 bytes on LP64) or a pinned 4 bytes?** **Exactly 4 bytes** — `i32` for
  the signed `GetLong` value, `u32` for the `unsigned long` header ids, **never**
  `core::ffi::c_long`/`c_ulong`. `tools/npcnav-oracle` builds the unmodified TU with
  a 4-byte-`long` shim (compile flags / stub-header typedef, not a source edit) so
  its fixtures are retail-shaped; goldens, retail pk3 `.nav` files, and the OpenJK
  referee all agree. General rule (Divergences D-9): Win32 `long` in a binary FILE
  format = 4 bytes; `c_long` in a compiled-ABI struct is the separate correct case.
  Overturns the earlier pass's LP64-`c_long` reading.
- **NAV-Q17** — *(Resolved: NAV-D2 / RULING 45, 2026-07-09.)* **Is a bare
  reference-cite to the libstdc++ `<bits/stl_heap.h>` (rulings 18/26) enough for a
  porter to reproduce the exact `push_heap`/`pop_heap` sift/tie order, or must the
  doc state the algorithm?** The doc **states it behaviorally** (Verification →
  "The libstdc++ heap sift"): the two-phase Floyd shape — `pop_heap` moves the root
  out, `__adjust_heap` percolates the hole down to a leaf under libstdc++'s
  child-comparison order, `__push_heap` sifts the saved value up from the leaf —
  implementable from the doc alone, with a reference-only header-path cite (no GPL
  text copied into the repo). The committed rank-order goldens are the enforcing
  gate: any sift-order mistake fails byte-comparison.

# Audit gh#31 step-010 - the renderfx closure packet

Audit of `.claude/packets/31/step-010/packet.md` at `1f561996` on `gh31-step-010-renderfx`. The auditor read every oracle cite, the live Rust ground on this branch, the census, DEC-54/DEC-37/DEC-44/DEC-66, and the gh#31 hand-forwards before the packet. Two mechanical rows are challenged. Three claims are disputed with evidence. The user rows carry three framing flags.

## Mechanical rows

### Row 6 - the distortion stage's inherited GL state: CHALLENGED

The premise is false. The oracle holds two separate chains inside the single-texture branch of `RB_IterateStagesGeneric`. The bind chain is `tr_shade.cpp:2163-2175` (distortion bind, else vertex-lightmap bind, else `R_BindAnimatedImage`). The state chain is `tr_shade.cpp:2177-2206`:

```c
if (tess.shader == tr.distortionShader && glConfig.stencilBits >= 4) { ... GL_State(0); }
else if (backEnd.currentEntity && (backEnd.currentEntity->e.renderfx & RF_FORCE_ENT_ALPHA)) { ... GL_State(...); }
else { GL_State( stateBits ); }
```

A plain `RF_DISTORTION` stage matches neither of the first two arms, so it reaches the `else` at `:2203-2206` and gets `GL_State(stateBits)`, its own stage state. The packet's sentence "which a distortion stage skips, so a distortion stage draws under whatever GL state the previous stage left" conflates the two chains. Only a distortion entity that also carries `RF_FORCE_ENT_ALPHA` diverts, into the force-alpha state the backend already ports (`pipeline3d.rs:4418`).

Consequence: the proposed action (draw under the stage's own state) is the faithful oracle behavior, not a divergence. Divergence note 4 describes a leak the oracle does not have and must not be written. The row resolves to "no divergence, no site note", and the packet prose at "The distortion stage arm" needs the same correction.

### Row 7 - the post-render partition and the LIFO order: CHALLENGED in part

Confirmed faithful: the per-surface partition, each surface's internal stage order, the surface-count cap with fall-through past 128 (`tr_backend.cpp:778-783`, `:655`), and the LIFO reversal (`:1008-1011`).

Challenged: the pass shape in the packet body and commit 3. The oracle interleaves capture and draw per deferred surface. Each drain iteration captures (when the entity qualifies, `:1144-1209`) and then draws that one surface (`:1211-1212`), so capture N reads a framebuffer that already holds deferred draws 1 through N-1, and each distortion entity samples its own capture content. The packet's shape ("encodes one capture per distinct deferred entity ... then draws the post-render list in a second pass") encodes every capture before any deferred draw, and the single `Option<ScreenImage>` slot means the last capture overwrites every earlier one. With two distortion entities in one frame, both stages bind the last entity's square, and neither square contains any deferred surface. Two cloaked players on screen is ordinary live surface (`cg_players.c:4935,6583,7968` all submit `RF_DISTORTION|RF_FORCE_ENT_ALPHA`, census 2,125). Remedies to put before the user with rows 3 and 7: one capture texture per distortion entity per frame, or a pass split at each capture boundary (end pass, copy, reopen with `LoadOp::Load`), which is the oracle's own order. The single committed distortion golden draws one distortion entity and would not catch this.

### Row 9 - the capture dedup and its retry: CLEARED, one wording correction

The transcribe-as-written default is right: set only after a successful copy (`:1207`), reset per frame (`:1006`), retry on a failed projection. But the mechanism is a consecutive-run compare, not a per-frame set. `lastPostEnt != pRender->entNum` (`:1144-1145`) compares only the last captured entity, so a deferred order A, B, A recaptures A. The packet's capture section says "one capture per distinct entity per frame" and commit 3 says "one capture per distinct deferred entity", which is a set-dedup the oracle does not have. In sort order one entity's surfaces sit contiguous, so the two usually agree, but the transcription instruction should state the run-compare. This folds into the row-7 reshape.

### Row 10 - `MAX_POST_RENDERS`'s home: CLEARED

`crates/mp/renderer/src/tr_backend.rs` is the twin that owns Raven's `tr_backend.cpp` statics (the `RB_RenderDrawSurfList` stub at `:750-819`), and the step-009 precedent is real (`LIGHTNING_RECURSION_LEVEL` at `crates/mp/renderer/src/tr_surface.rs:53-57` with the live arm in `pipeline3d.rs`). The const value 128 matches `tr_backend.cpp:655`.

## User rows - framing flags only, not ruled

- **Row 1.** The 2,125 count is confirmed (below). No framing change. The phrase "second-largest dark row" reads right only when `RF_NOSHADOW` (65,349) counts as the largest dark row until row 8 closes it.
- **Row 2.** The default is sound: wgpu texture copies take `wgpu::TexelCopyTextureInfo { texture: &Texture, ... }` (the shape `gpu.rs:417-437` already uses), and a `TextureView` offers no way back to its texture, so the threading is genuinely needed. Both targets already carry `COPY_SRC` (`gpu.rs:118`, `:380`) and the windowed caller already holds `frame.texture` (`render_thread.rs:128-130,145`). The call-site count is disputed below.
- **Row 3.** Two facts change the framing. First, the single `Option<ScreenImage>` slot cannot serve two distortion entities in one frame (row 7 above), so the shape choice and the pass choice are one ruling. Second, "reproduces the oracle's sampling exactly" misses row order: `glCopyTexImage2D` stores the rect bottom-up (`t = 0` samples the rect's bottom row), and `copy_texture_to_texture` stores it top-down (`v = 0` samples the top row), so identical texture coordinates sample the square vertically flipped against the oracle. File-loaded images agree between the two worlds, and only this framebuffer copy diverges. The port needs a row flip decision (flip `v` for `screen_image` items, or record a divergence note).
- **Row 4.** One defect condition can be vacuous. The mirror is a positional reflection: `cX = vidWidth - x - rad/2` picks the square reflected about the vertical centerline, and the square itself is not flipped. A distortion sprite centered horizontally ("over the middle of them") captures the same square with or without the mirror term, so the "unmirrored means corrected away" check discriminates nothing there. The scene must place the distortion sprite off-center horizontally. Determinism is confirmed: no body in scope draws a random number (verified by grep over all six bodies), the capture is a byte-exact copy of main-pass pixels the existing goldens already prove deterministic, and DEC-66's fixed-dt rule holds with no reseed need.
- **Row 5.** Confirmed contained: `scene_renderfx_tint` holds the only two `RF_FORCE_ENT_ALPHA` submissions in any committed fixture (`scene_golden.rs:697-698`), and no fixture or harness submits `RF_DISTORTION` or `RF_FORCEPOST` (grep over `tests/` and `src/bin/`).
- **Row 8.** The conversion set targets the wrong ghoul2 site. `tr_ghoul2.rs:2459-2462` is the deferral note for the `RF_NOSHADOW` write (oracle `:3525-3528`, the `bInShadowRange` suppression), not a read. The ghoul2 read, where the MP-versus-SP projection asymmetry actually lives, is deferred at `tr_ghoul2.rs:840-842` and `:909-911` (the stencil- and projection-shadow pushes). Converting only the packet's two sites leaves the ghoul2 shadow-add read unmarked and pins the asymmetry note on the write site. Also, the asymmetry sentence over-claims: SP tests the flag in the projection arm at the ghoul2 site only (`oracle/code/renderer/tr_ghoul2.cpp:2801`), and SP's md3 projection arm does not test it (`oracle/code/renderer/tr_mesh.cpp:416-420`), matching MP. The marker text must scope the asymmetry to ghoul2.
